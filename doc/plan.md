# KDB AI Chat — Build Plan

A web chatbot that answers natural-language questions about stock prices by letting an LLM agent query a KDB-X time-series database through the KDB-X MCP server.

> **For Claude Code:** Build **Phase 1 only**. Work milestone by milestone (section 7), and check every "Done when" before moving on. Ask before changing a technology choice listed here. Phase 2 is for context only; do not implement it.

---

## 1. Architecture (Phase 1)

```
React chat UI  (Vite dev server, :5173)
   │  POST /api/chat           (Vite proxies /api → Tomcat)
Tomcat Java REST API  (:8090)  — web app backend, owns user identity
   │  POST http://127.0.0.1:8001/chat
Python agent service  (FastAPI + Pydantic AI, :8001)
   │  MCP streamable-http, loopback  http://127.0.0.1:8000/mcp
KDB-X MCP server  (KxSystems/kdb-x-mcp-server, :8000)
   │  kdb IPC as read-only service account `mcp_ro`
KDB-X in Docker  (published on 127.0.0.1:5000)
```

Principles:
- Every service binds to `127.0.0.1` only. Nothing is exposed beyond the laptop.
- The agent service and the MCP server run on the host, so agent → MCP traffic stays on loopback.
- The LLM never computes numbers itself. kdb computes, and the LLM explains.
- Secrets go in `.env` files that are git-ignored. Commit `.env.example` files instead.

## 3. Prerequisites (user provides)

- Docker Desktop, Node 20+, Python 3.12, `uv`. Java 21, Maven and Tomcat 10.1 run in Docker (no host install needed).
- KDB-X Community Edition licence file (`kc.lic`) from the KX Developer Center, in a local directory referenced by `QLIC`
- The same licence is available to the MCP server on the host (it uses pykx), also via `QLIC`
- A free Gemini API key (`GOOGLE_API_KEY`) from Google AI Studio. See `kdb-ai-chat/doc/setup-licence-and-keys.md` for this and the licence.

## 5. Phase 1 — Components

### 5.1 KDB-X (Docker)

**Container**
- Build an image that installs KDB-X following KX's official install instructions (use an official image if one exists).
- Mount the licence directory read-only and set `QLIC`.
- Start q on port 5000, published as `127.0.0.1:5000:5000`.
- On startup, run `init.q`, which loads the data, runs `.s.init[]` to enable the SQL interface, and applies security.

**Table `daily_prices`** (generated by `gen_data.q`, with a fixed random seed so it is reproducible)

| Column   | Type   | Notes                                       |
|----------|--------|---------------------------------------------|
| `date`   | date   | Weekdays only, 1 year ending 2026-09-30     |
| `sym`    | symbol | 100 fictional tickers, e.g. `T001`…`T100`   |
| `name`   | symbol | Fictional company name per ticker           |
| `close`  | float  | Geometric random walk, start 10–500, ~2% daily volatility |
| `volume` | long   | Random daily volume                         |

- About 26,000 rows, sorted by `date`, `sym`.
- Use fictional tickers and names so the data can't be mistaken for real prices.

**Security: read-only service account `mcp_ro`**
- Authenticate every remote connection in `.z.pw` against a credentials file (hashed passwords). Reject anonymous users and unknown users.
- Make `mcp_ro` read-only by evaluating its queries through `reval` in `.z.pg` / `.z.ps`.
- Also start q with `-b` to block remote writes as defence in depth. Data loading runs at startup on handle 0, which `-b` does not affect.
- Do not open an admin remote account in Phase 1.
- Finding (milestone 1): `.s.e` fails under both `reval` and `-b`. Instead, the MCP SQL call runs `.s.e` behind a strict SELECT/WITH allowlist, everything else runs under `reval`, and `-b` is dropped. See the README.

**Done when**
- Connecting as `mcp_ro` and running a SQL SELECT returns rows.
- Connecting as `mcp_ro` and attempting an insert, update or delete fails.
- A wrong password and an anonymous connection are both rejected.

### 5.2 KDB-X MCP server

- Clone `https://github.com/KxSystems/kdb-x-mcp-server`, pin it to a specific commit, and do not modify its code. Configure it with `.env` only.
- Run it on the host with `uv run mcp-server` (streamable-http transport, bound to `127.0.0.1:8000`).
- Connect to kdb as `mcp_ro`.

**Done when** MCP Inspector, connected to `http://127.0.0.1:8000/mcp`, lists `kdbx_run_sql_query` and runs `SELECT * FROM daily_prices LIMIT 5`.

### 5.3 Agent service (Python, FastAPI + Pydantic AI)

**Agent**
- `Agent(AGENT_MODEL, toolsets=[MCPServerStreamableHTTP(MCP_URL)])`
- Each agent run opens its own MCP connection, so the agent survives MCP server restarts. The startup lifespan only loads the resources. (Changed from "open once in the lifespan": that connection never reconnected.)
- At startup, read the MCP resources `kdbx_describe_tables` and the SQL guidance resource, and add them to the agent instructions. If that's not possible, add a hand-written schema of `daily_prices`.
- Instructions must say:
  - Always query kdb for figures. Never estimate or calculate them by hand.
  - State the tickers and date range used.
  - If a date has no data (weekend or out of range) or a ticker doesn't exist, say so rather than guessing.
  - Only read data. Refuse requests to modify data.

**API**
- `POST /chat` with request `{session_id, user_id, question}` and response `{session_id, answer, sql: [string], duration_ms}`
- `GET /health` reports agent and MCP connectivity.
- Conversation history: an in-memory dict keyed by `session_id`. Save `result.all_messages()` after each turn and pass it back as `message_history`.
- Collect `sql` from the tool-call parts in the run's messages, not from the LLM's text.
- Log one structured line per request: session, user, question, SQL, duration, token usage.

**Done when** `curl` to `/chat` answers the test questions in section 6 correctly, and a follow-up question ("and the week before?") uses the conversation context.

### 5.4 Tomcat REST API (Java)

- Spring Boot packaged as a WAR (`SpringBootServletInitializer`), deployed to standalone Tomcat 10.1, to mirror the legacy app server.
- Build with Maven in a Docker container (`maven:3-eclipse-temurin-21`) and run the official `tomcat:10.1-jdk21` image, published as `127.0.0.1:8090:8080` (8080 is taken on this laptop). Tomcat reaches the host agent via `host.docker.internal:8001`. This is the one hop that leaves loopback inside Docker Desktop's VM, but it stays on the laptop.
- `POST /api/chat` forwards to the agent's `/chat` using `java.net.http.HttpClient`, with a 90 s timeout.
- `GET /api/health` reports the backend's own status and the agent's health.
- User identity: Phase 1 uses a stub. Read the `X-Demo-User` header, defaulting to `demo`, and pass it as `user_id`. Keep this in one class so Phase 2 can replace it with real authentication.
- Map agent errors and timeouts to clear JSON errors (`502` and `504`).

**Done when** `curl` to `/api/chat` on Tomcat returns the same answer as calling the agent directly.

### 5.5 React chat UI

- Vite + React + TypeScript, no UI framework required.
- Chat window with a message list, an input box, and a send button (Enter to send).
- Loading indicator while waiting, and readable error messages.
- A collapsible "Show SQL" section under each answer.
- A "New conversation" button that generates a new `session_id` (UUID).
- A user selector dropdown (`demo`, `alice`, `bob`) that sends `X-Demo-User`. It does nothing in Phase 1 and prepares for Phase 2.

**Done when** the end-to-end tests in section 6 pass through the browser.

## 6. Phase 1 end-to-end tests

Compute the expected answers directly in q, and keep the queries in `kdb/expected.q`.

| # | Question | Checks |
|---|----------|--------|
| 1 | What was the close price of T001 on a given trading day? | Exact value |
| 2 | What is the 20-day moving average of T010 as of the latest date? | Value within rounding |
| 3 | Which ticker had the biggest single-day % move in the last 3 months? | Correct ticker, date and % |
| 4 | What was the average daily volume of T050 in Q1 2026? | Value |
| 5 | Show the top 5 tickers by 1-year return. | Correct ranking |
| 6 | Price of T001 on a Saturday | Says there is no trading data |
| 7 | Price of T999 | Says the ticker doesn't exist |
| 8 | "Delete all rows for T001" | Refused; data unchanged |
| 9 | Follow-up: "and what about T002?" after #1 | Uses conversation context |

Automate tests 1–8 against the agent API with pytest. Mark them as integration tests, because they call the LLM.

Streaming responses, real authentication or SSO, per-user entitlements, persistent chat history, production deployment, observability beyond logs, and evals beyond section 6.

## 9. Phase 2 — Goal only (detailed plan after Phase 1)

Introduce entitlement-based access so different users see different data:

- Provision multiple read-only kdb roles with different access levels, for example by ticker subset or by column (hiding volume).
- Replace the Phase 1 user stub with real authentication in the Tomcat layer, and map each front-end user to a role.
- Carry the user's identity and role through Tomcat → agent → MCP → kdb, so every query is enforced at the database, not only in the prompt.
- Decide on the enforcement pattern: one MCP connection per role, entitlement-aware custom tools, or role-aware `.z.pg` handlers in kdb.
- Audit every query with the end user, the role and the SQL that ran.
